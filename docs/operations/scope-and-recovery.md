# Deployment scope and shared recovery

Part of [Shared deployment operations](index.md).

Etherplan's local state file, journal, and process lock remain the default for development. A production apply passes a shared deployment scope and implementations of `stateStore`, `journalStore`, `lockProvider`, `journalCipher`, and `signerProvider` to `applyPlan`. The AWS reference implementation uses DynamoDB for conditional state, journal, and lease writes; KMS envelope encryption for signed bytes; and S3 for immutable plans. The signer service adapter sends transaction requests to a separate signer process and receives only an address or signed transaction.

A scope contains `project`, `environment`, `chainId`, `genesisHash`, and `label`. The chain values must match the saved plan. A deployment lock covers the complete scope. Signer locks cover the chain ID, genesis hash, and signer address across every project, environment, and label in the same DynamoDB table. Deployments sharing a signing account must use that same coordinating table; separate tables cannot share the lease or signed history. The lock provider returns monotonically increasing fencing tokens. Every DynamoDB state or journal transaction checks the deployment and signer tokens, holder identity, and live expiry. A journal write that waits behind another write checks the leases when it runs. A lost or expired lease stops the next signature, broadcast, or state write; a renewal that only times out or cannot reach the table is retried while the lease is still valid.

Journal records include sequence, predecessor hash, plan hash, chain identity, action ID, phase, write time, and applying principal. Signed transaction bytes are encrypted before the journal store sees them. Recovery validates the complete ordered hash chain, decrypts the signed records of the plan being applied and of unresolved transactions, checks the signed envelope against the pinned plan and durable intent, and resends the exact persisted bytes. An open journal then validates each record that it adds against its predecessor. An unfinished transaction for another plan stops a production apply before any write. Each signed append also writes a signer-wide index entry with its source project, environment, and label in the same fenced DynamoDB transaction. Before signing, apply reads the account nonce of each signer at the configured confirmation depth. An indexed transaction with a lower nonce is settled: the chain used its nonce at that depth, so its signed bytes cannot be included. Apply does not check which transaction used that nonce. Each other indexed transaction needs a canonical receipt at that depth. A missing or orphaned receipt stops the new deployment until the earlier one is resolved.

Signer-history checks use the current deployment's already-open journal, including later durable appends. During a remote apply, each signer's index is read once after its lease is acquired. Source journals are loaded and their hash chain and head are validated once. Later checks reuse that evidence and add new signatures from the open journal. The held signer leases prevent other coordinated writers from adding signatures for those signers. The nonce read, and the receipt and canonical-block checks of each transaction that is not settled, still run before signer reuse. A new apply loads fresh history; a lost lease stops further signing and broadcasting.

A pipelined group stores its intents in as few journal transactions as the store accepts. Each transaction is atomic and has one head update, so an interrupted group leaves a valid journal with some or all of its intents and no signature. The group's transactions are then signed, and their bytes encrypted, a bounded number at a time. Their signed records are stored one at a time in plan order, and no broadcast starts before all of them are durable. A failure can lose a signature that was not stored yet. A rerun makes that signature again and never repeats a stored one.

Before a group signs, apply checks its prerequisites at one block. The checks overlap, a bounded number at a time, and share reads that have the same client, method, arguments, and block. Apply then confirms that the block is still canonical. The final check of every resource before the state commit works the same way. A later check selects a new block and reads the chain again.

During one apply, successful creation verification supplies reusable deployment evidence. Later checks still read the current runtime and spec getters and check the creation block's canonical hash. They do not fetch the same creation transaction, receipt, or historical factory code again. Pinned-runtime checks also refresh each child's runtime and parent getter. This evidence belongs to that apply and RPC client; a new apply validates persisted proofs against the chain again.

When an apply fails after some deployments completed, a corrected plan reads verified creation proofs from the same scoped journal. It validates the journal chain and head without decrypting signed bytes, then checks each candidate proof against the live chain and current spec. The new plan pins accepted proofs; apply checks that their journal records still exist under the writer lease before recording recovered deployments in state. Programmatic planners can pass `journalRecords: await readStoredJournal(backend.journalStore, scope)` to `createPlan`.

Local applies on one host and OS user coordinate the same chain and signer through a durable registry under `~/.etherplan/local-signers`. A second local journal is checked against durable signatures from the first before signing. Keep this directory with the journals during recovery. Local files on different hosts or under different OS users cannot share that registry; use one production backend table when those runners share a signing account.

Production applies require an explicit positive `confirmations` value in deployment policy. Within one active plan, dependent waves can advance after one canonical receipt. Apply requires the configured confirmation depth before it commits state or another plan reuses the signer. On restart, apply validates saved receipt evidence against the chain. During that apply, it reuses validated receipt data and checks each distinct inclusion block before later execution. A changed canonical block stops apply and reopens verified actions for recovery. Local file applies use one confirmation unless `confirmations` is supplied. Confirmation depth is chain-specific and does not guarantee permanent finality.
